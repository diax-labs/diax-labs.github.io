Release Status & Setup

Choose the Trust Boundary First

DiaX gives an AI two useful output modes with different security properties:

  • Untrusted or automated output: generate JSON with string content and object-form edges, validate it, then pass the validated fields to DiaX.
  • Trusted authored output: generate or edit MDX/JSX in a reviewed code workflow, where normal React components and Tailwind classes can provide richer presentation.

MDX and JSX are executable code, not a safe serialization format. Never compile, import or evaluate model-generated MDX/JSX from an untrusted request inside your application process. Use JSON for that boundary, or run code generation in a reviewed and appropriately sandboxed workflow.

Ask the model for a constrained JSON object. Prefer object-form edges: from, to and label remain separate fields, so a validator and a repair loop can identify the exact failure without reparsing a compact string.

Treat parsed JSON as unknown. Validate its structure with an application-owned JSON Schema, Zod, Valibot or equivalent, then use DiaX validation for graph-level problems such as duplicate IDs and missing endpoints:

DiaX publishes a baseline schema at diax/schemas/diax.json. An AI-facing schema should usually be narrower—for example, require object-form edges and a small allowlist of node types.

React escapes string content, but validation is still required for correctness, resource limits and application policy.

This pattern works because:

  • DiaX topology is data-driven — IDs, nodes and object edges are easy to validate and repair.
  • Tailwind classes are composable — trusted source can use an existing design system.
  • MDX combines prose and JSX — useful in a reviewed authoring pipeline, not as an untrusted runtime payload.

AI Agent Best Practices

1. Default to object edges

Object edges cost a few more tokens but produce better diagnostics and avoid escaping or delimiter ambiguity. Reserve the string shorthand for trusted, hand-authored diagrams where terseness matters.

2. Keep rendering choices application-owned

Register a small allowlist of nodeTypes and themes in application code. Let the model select a known type or preset; do not let untrusted JSON inject arbitrary JSX, imports or component names.

3. Do not let the model invent vendor identity

Treat a provider or product mark as optional presentation, not graph semantics. The model may select an application-approved provider ID only when the source text names it unambiguously. Application code maps that ID to a trusted NodeCard.icon, ActorNode.avatar or nodeTypes renderer.

Use these generation rules:

Icons and avatars should normally be decorative (aria-hidden="true"); the visible node name owns the accessible identity. The application owns the asset source, license/trademark review, targeted import and bundle cost. DiaX does not fetch logos or ship a vendor catalogue. See the vendor identity recipe for a compiled nodeTypes example with an explicit fallback.

4. Choose one layout owner

When the model is explaining topology, generate a Diagram Definition and let DiaX place it. Do not smuggle manual positions into an automatic Diagram:

When the expression is a report, comparison, code walkthrough, mock UI or other authored composition, let JSX/CSS own layout and use the isolated Connect leaf for geometry:

Do not combine these into a generated mode prop. The model should decide from the job: topology data → Diagram; authored DOM composition → Connect. Keep relations centralized in both cases.

5. Feed diagnostics back to the model

Keep code, path, message and hint intact when asking an agent to repair invalid output. Do not reduce diagnostics to one generic "diagram failed" string: field-level feedback is what makes an AI loop predictable.

Run the repaired response through the same structural and graph validation again. Set a small retry limit and show the final diagnostics to the author instead of silently rendering a partial graph.

The Playground's JSON and Mermaid editors use the same focused policy for interactive authoring: validate before render, preserve the first diagnostic subject and show one supported next edit. The projection remains private to the product surface—it is not a second public diagnostic interface, and it never exposes routing coordinates as an AI repair control.

Internally, the Playground and Agent first-success verifier share one versioned repair catalog for Core diagnostic codes. It binds preserve policy → repair scope → supported action → retry stage and includes the catalog hash in verifier identity. This is evidence that DiaX's own product paths do not drift; it is not a catalog export, a schema extension or a requirement for application agents.
