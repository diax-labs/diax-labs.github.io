Release Status & Setup

Pre-1.0 Theme Import Migration

Theme authoring moved out of the headless diax root and into diax/themes. Framework users who only pass theme="github" do not need to change component code.

The global registerTheme(), getTheme() and getThemeNames() functions were removed. Pass custom themes as values so SSR, multiple bundles and Module Federation remotes cannot observe divergent registries:

Pre-1.0 Framework Interface Migration

The React root no longer exports its internal generic Diagram, the shallow useDiagramBuilder state wrapper, or the useTheme convenience hook:

Use FlowDiagram or Mindmap for the high-level rendering lifecycle. Keep dynamic nodes and relations in ordinary useState/useReducer or an application store, and keep theme selection in ordinary React state. The low-level useDiagram + DiagramCanvas + DiagramNode + DiagramEdges composition remains public for custom renderers.

React JSX topology moved to its own authoring entry. The syntax remains supported and now exposes the complete shared Relation contract; only the import changes:

The root @diax/react FlowDiagram now accepts data only. If nodes and relations already exist as arrays, keep the root import and pass them directly instead of mapping them into JSX markers.

Rich edge events now live only on relation objects. If you used the low-level React DiagramEdges.edgeEvents map, move each handler onto the corresponding relation. This also gives parallel edges an unambiguous event owner and enables the same behavior in all official adapters:

Vue and Solid no longer export useTheme. Theme selection is ordinary framework state; replace the wrapper with Vue ref<ThemeInput>() or Solid createSignal<ThemeInput>(), then pass the value to FlowDiagram. This keeps Theme policy out of framework roots and avoids a second state abstraction.

Vue's low-level useEdgeRenderer() now returns Core render data without a translation layer. Update custom SVG renderers to the resolved names below:

The composable no longer accepts or returns a global strokeWidth; set the visible path width from path.strokeWidth with your renderer's own fallback. It now returns only { paths, markers }.

Solid custom renderers now receive Accessors. This follows Solid's fine-grained reactivity model and keeps authored node DOM, focus and local state stable when highlight state changes:

Apply the same node() / state() change to functions in a Solid nodeTypes registry.

The Core getNodeDisplayOpacity() helper now returns 0.25 for a dimmed node (previously 0.2). All official adapters consume that single policy, matching the existing opacity-25 renderer examples and preventing framework-specific visual drift.

Pre-1.0 Mermaid Importer Migration

The concrete mermaidAstAdapter and its parser-adapter type are now internal. Normal callers should use the deep importer; a tool that already knows the diagram family can use the corresponding transformer directly:

Parser backend replacement is not a public plugin lifecycle. parseMermaid() owns detection, dispatch, empty-input handling and diagnostics so tools do not reproduce that coordination.

Migrating from Mermaid

DiaX can import a supported Mermaid subset into a normalized DiaxAST. The importer currently covers flowchart, class, state, ER, requirement and mindmap families; it is not a full Mermaid renderer.

After (DiaX)

If you previously imported the high-level component from @diax/ui-react, move that import to @diax/ui-react/mermaid. The root now intentionally contains only parser-free DOM presets.

Install @diax/ui-react, @diax/react and @diax/mermaid, import @diax/ui-react/styles.css once from the application's global stylesheet, and render the existing source through the supported-subset component:

Use parseMermaid() when a migration tool, CI check or custom renderer needs the normalized AST and diagnostics rather than a React component:

The AST contains nodes, normalized edges and optional layout metadata. It does not return the legacy { nodes, relations } shape; that shape belongs only to the explicitly named parseMermaidFlowchart() compatibility function.

Or skip Mermaid import and write the topology directly in DiaX:

Migrating from react-archer

First decide who should own placement. If your flex, grid, Tailwind and semantic HTML are part of the visual explanation, migrate to Connect and keep that DOM. If the CSS only arranged generic boxes and you want the library to place them, migrate to automatic Diagram instead.

react-archer puts outgoing relations on source wrappers. Connect keeps endpoints on the real DOM but moves topology into one reviewable relation list.

Before (react-archer)

After: keep the authored layout with Connect

Start without anchor overrides. Connect chooses facing edges from the measured boxes and keeps them updated as the authored layout reflows. Add an explicit anchor only when one attachment side carries real meaning, not as routine migration boilerplate.

Alternative: hand placement to Diagram

When the old flex/grid was incidental, use FlowDiagram with the same centralized relations:
