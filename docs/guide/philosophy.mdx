# Philosophy (/docs/guide/philosophy)





The Product Gap [#the-product-gap]

Existing tools optimize for different jobs:

* **Mermaid** prioritizes a portable text DSL and a consistent SVG renderer.
* **D2** prioritizes declarative source and compiled SVG/PNG output.
* **React Flow** provides a capable interactive editor surface with positioned React nodes.
* **Excalidraw** prioritizes free-form visual sketching.

The remaining gap is code-defined diagrams whose nodes must be ordinary application DOM: existing
design-system components, semantic HTML, live state and responsive CSS should remain usable without
giving the diagram runtime ownership of their presentation.

The Insight [#the-insight]

> **Structure and presentation should be completely decoupled.**

This is the same insight that powers:

* **Headless UI** (Radix) — behavior without styling
* **Headless CMS** (Sanity) — content without rendering
* **CSS-in-JS** — styling as data, not files

DiaX applies this to diagrams:

* **You describe** the structure (nodes, edges, relations)
* **DiaX computes** the layout (positions, paths, coordinates)
* **You render** with your own JSX, Tailwind, Vue templates, or vanilla DOM

There are two ownership modes behind that idea:

* **Diagram mode** — you provide topology and node content; DiaX also owns automatic layout.
* **Connect mode** — you keep an existing DOM/CSS layout; DiaX only measures and connects targets.

Both are public, but they remain separate loading seams: Diagram components come from `@diax/react`;
authored-DOM connection comes from `@diax/react/connect`. Neither interface silently switches layout
ownership based on props or child shape.

MDX + JSX + Tailwind + DiaX [#mdx--jsx--tailwind--diax]

This combination is a strong fit for trusted, code-reviewed technical content:

```mdx title="my-page.mdx"
import { FlowDiagram } from '@diax/react';

# System Architecture

Here's how our services connect:

<FlowDiagram
  nodes={[
    { id: 'api', content: 'API Gateway' },
    { id: 'auth', content: 'Auth Service' },
    { id: 'db', content: 'PostgreSQL' },
  ]}
  relations={['api->auth', 'auth->|JWT|db']}
  density="spacious"
/>
```

Why this works:

1. **Markdown for prose** — headings, paragraphs, lists, links
2. **JSX for diagrams** — interactive, type-safe, component-based
3. **Tailwind for styling** — consistent design system, utility classes
4. **DiaX for layout** — automatic positioning, edge routing, animations

The result: diagrams that look like they belong in your product, not like they were generated by a separate tool.

MDX and JSX are executable application source. They belong in a trusted authoring and review
workflow; untrusted model output should cross the application boundary as validated JSON instead.

AI-Native Design [#ai-native-design]

DiaX is designed from the ground up for the AI era:

```json title="AI-friendly JSON"
{
  "nodes": [
    { "id": "browser", "content": "Browser" },
    { "id": "api", "content": "API Server" }
  ],
  "relations": [
    { "from": "browser", "to": "api", "label": "HTTPS" }
  ]
}
```

This JSON is:

* **Easy for LLMs to generate** — simple nodes and explicit object edges
* **Easy to validate** — a runtime schema checks structure and DiaX diagnostics check graph semantics
* **Easy to render** — pass only validated `nodes` and `relations` to `FlowDiagram`

TypeScript types do not validate JSON at runtime. Parse model output as `unknown`, enforce size and
field allowlists, then render it as data. See the [AI Integration guide](/docs/guide/ai-integration)
for the full trust-boundary workflow.

1\. Headless Core, DOM Bindings [#1-headless-core-dom-bindings]

The `diax` core computes topology, bindings and edge geometry. Framework packages turn those results
into real DOM nodes plus an SVG connection layer, while the application remains responsible for node
content and styling.

2\. Progressive Disclosure [#2-progressive-disclosure]

* **Quick Start**: `<FlowDiagram>` / `<Mindmap>` — current Alpha compatibility entry points
* **Custom Rendering**: `renderNode` — custom styling, same layout
* **Headless**: `useDiagram()` — binding data for library authors and advanced rendering

Start simple, go deep when you need to.

3\. Framework Agnostic Core [#3-framework-agnostic-core]

The `diax` core package is pure TypeScript with zero runtime dependencies. The adapters are not yet
interchangeable in every capability:

| Package         | Current role            | Reactive primitive |
| --------------- | ----------------------- | ------------------ |
| `@diax/react`   | Reference Alpha binding | hooks              |
| `@diax/vue`     | Official Alpha adapter  | computed/ref       |
| `@diax/svelte`  | Official Alpha adapter  | stores             |
| `@diax/solid`   | Official Alpha adapter  | signals            |
| `@diax/vanilla` | Official Alpha adapter  | imperative         |

“Official Alpha” means an implementation is maintained in this repository. It does not claim full
parity in rich labels, events, SSR, measurement updates or accessibility until the shared contract
matrix passes.

4\. Mermaid Import [#4-mermaid-import]

DiaX imports a supported Mermaid subset into its normalized AST:

```ts title="mermaid-migration.ts"
import { parseMermaid } from '@diax/mermaid';

const result = parseMermaid(`
  flowchart LR
  A[Start] --> B{Decision}
  B -->|Yes| C[Execute]
`);

if (!result.ast) {
  throw new Error(JSON.stringify(result.diagnostics));
}

console.log(result.diagramType, result.ast.nodes, result.ast.edges);
```

This is an import path, not full Mermaid compatibility. Unsupported families and unsupported syntax
produce diagnostics instead of being guessed or silently rendered as another diagram type.

5\. Size Is a Release Contract [#5-size-is-a-release-contract]

Package size is measured from real build artifacts in CI, including a complete-entry ceiling. We do
not publish a fixed gzip claim here while that budget is still a release gate, and we do not infer
consumer bundle size from source-module tree shaking alone.

6\. Accessible by Design [#6-accessible-by-design]

Diagrams are often a black box for screen readers. DiaX keeps node content as native HTML and emits
valid relationship hints such as `aria-flowto`. It deliberately avoids assigning anonymous group or
button roles to visual-only node wrappers. Those hints do not replace meaningful headings, links,
buttons, text alternatives or keyboard behavior in your node components; the accessibility contract
remains part of the framework test matrix.
