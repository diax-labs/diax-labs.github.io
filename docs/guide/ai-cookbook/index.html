Classify the visual before generating code

The most important AI decision is not color or arrow style. It is who owns layout.

User intentGenerateWhy
System architecture or call graphDiagram JSONTopology should determine placement
Organization tree or mind mapDiagram JSONHierarchy is the visual structure
Existing Mermaid contentMermaid source, then importPreserve portable text input
Decision with evidence cardsReviewed Connect JSXReport composition should remain authored DOM
KPI cards with causal arrowsReviewed Connect JSXMetrics need responsive CSS and semantic HTML
Before / After comparisonReviewed Connect JSXColumns and annotations own the story
Promotion timeline or roadmapReviewed Connect JSXTime, prose and milestones need deliberate composition
Reusable application graphDiagram data + nodeTypesData remains serializable; presentation stays allowlisted

Use JSON at an untrusted runtime boundary. Generate JSX only in a trusted repository workflow where the result is reviewed like application code.

This page supplies question-first recipes. Use the Agent-first Workflow to carry the selected recipe through validation, the exact built preview, final-use-size review and truthful export or sharing.

Recipe: grounded RAG architecture

Treat retrieval as an architecture question, not as a new DiaX mode. Start from two independently owned paths:

  • the online question path authorizes intent, checks a policy-aware cache, retrieves and reranks evidence, then preserves citation identity in the answer;
  • the versioned knowledge path chunks reviewed sources, records revisions and access metadata, then updates the durable index consumed by retrieval.

Use ordinary Diagram nodes and relations because the topology should determine placement. Semantic groups can name the two paths and their shared parent system; SystemNode, DataStoreNode and EvidenceNode remain replaceable DOM presentation. A cache return or reranker feedback relation is an ordinary stable edge, not a hand-authored bend point.

Before generating the artifact, require the authorization boundary, cache key, index revision, retrieval contract and citation identity as verified facts. Do not invent RagDiagram, retriever node types in Core, coordinates or a vendor-logo registry.

At narrow reading widths, keep node metadata, group titles and relation labels at their intended size and make the wide canvas explicitly horizontally scrollable. Do not scale thirteen rich nodes down until the topology fits 320px: that produces a recognizable thumbnail, not a readable system review.

Recipe: repository-grounded architecture evidence

For source-code architecture reviews, citations are authored facts—not inferred graph metadata. Resolve and verify them in an agent or build workflow before rendering:

The authoring step must verify the public HTTPS repository, full 40-character commit, blob, and line range before producing a stable link. Missing evidence fails closed. After that check, pass the trusted link into EvidenceNode and use Connect only for a declared relation such as “supports this decision.” DiaX Core and framework adapters do not need Git, filesystem, GitHub, or network access.

Do not turn file proximity or dependency reachability into an unverified runtime-impact claim.

Repeatability checklist

  • Stable IDs survive prompt retries and content edits.
  • Object relations make repair paths explicit.
  • Generated JSON has product-specific size and type limits.
  • JSX generation happens only in a reviewed code workflow.
  • One surface has exactly one layout owner.
  • The result uses semantic HTML before decorative wrappers.
  • Long text, empty content, mobile width and dark mode are part of acceptance.
  • Export is deterministic; screenshots are outputs, not the source of truth.

The goal is not to make AI draw pixels more creatively. It is to give AI a constrained, inspectable web-native language whose output can be repaired and reproduced.
