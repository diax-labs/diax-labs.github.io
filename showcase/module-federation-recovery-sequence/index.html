Question-First Recipe

How does a federated feature recover without reusing stale remote assets?

Use authored message rows with stable IDs. Distinguish solid requests, dashed returns, retryable transport failure and the new attempt without introducing message coordinates or a Sequence mode.

Use this shape when

  • Explain lazy remote activation, a visible retryable failure and a successful retry
  • Show why the remote container and descendant chunks must move together to a new attempt-scoped base path

Choose another shape when

Avoid this recovery sequence for a shared-runtime version mismatch; that incompatibility needs deployment repair rather than a Retry loop.

Facts the author or agent must know first

  1. The attempt-scoped base path for the container and feature chunks
  2. The exact host loading and error states
  3. The successful ready-state acknowledgement
  4. The user action that activates the remote
  5. Which failures are retryable

English

Create a module-federation recovery sequence with @diax/react/connect. Preserve explicit activation, host loading/error states, a retryable 503, one visible Retry action, an attempt-scoped replacement asset graph and a final ready acknowledgement. Use stable message IDs and an accessible narrow-screen transcript. Do not model a version mismatch as retryable and do not add message coordinates or a sequence mode.

中文

使用 @diax/react/connect 创建模块联邦恢复时序。保留显式激活、Host loading/error 状态、可重试的 503、一个可见 Retry 操作、按 attempt 整体替换的资源图和最终 ready 回执。使用稳定消息 ID 与窄屏可访问 transcript。不要把版本不兼容建模为可重试，也不要添加消息坐标或 sequence mode。
